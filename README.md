# Highload E-Commerce Platform Core (Backend Core Architecture)

Архитектурное ядро высоконагруженной E-commerce платформы с открытым исходным кодом. Система спроектирована с нуля для обеспечения стабильной производительности под высокой нагрузкой (**3000 RPS**, валидировано в ходе нагрузочного тестирования через Locust).

Главная инженерная цель проекта — **полная разгрузка реляционной СУБД PostgreSQL от горячего трафика**. За счет построения многоуровневой системы асинхронных микросервисов, распределенного NoSQL-кэширования и очередей задач, в PostgreSQL изолированы только мастер-сущности и транзакционные данные (`users`, `goods`, `receipts`).

---

## 🏗️ Архитектура и реализованные решения

### 1. Гибридная микросервисная архитектура (CQRS) & Маршрутизация
Первоначально платформа базировалась на монолитной структуре Django. В ходе нагрузочного тестирования синхронные Django Views приложения `goods` стали узким горлышком (bottleneck) при Highload-чтении каталога. 
* **Решение:** Доменная область каталога товаров (`goods`) декомпозирована и вынесена в отдельный асинхронный микросервис на **FastAPI** с использованием **SQLAlchemy 2.0 Async** и **Pydantic**.
* Перед бэкенд-слоем развернут балансировщик **Nginx**, который осуществляет маршрутизацию трафика: административная панель и транзакционные операции направляются на Django, а весь тяжелый трафик чтения каталога — напрямую на FastAPI.

### 2. Распределенная NoSQL-архитектура (Redis Sharding & Isolation)
Для предотвращения взаимной блокировки потоков данных и оптимизации оперативной памяти, NoSQL-слой функционально фрагментирован и изолирован по **4 независимым инстансам Redis** в Docker-контейнерах. Для каждого инстанса настроена своя оптимальная стратегия персистентности данных (**AOF + RDB**):
* **Инстанс 1 (Сессии и корзины):** Оперативное хранение, логика слияния корзин, защита отrace conditions.
* **Инстанс 2 (Кэш верстки):** Фрагментарное кэширование динамических элементов интерфейса.
* **Инстанс 3 (Брокер Celery):** Брокер сообщений для распределенной очереди асинхронных задач.
* **Инстанс 4 (Сухой каталог):** Интенсивное Highload-чтение товаров. Интегрирован модуль **RediSearch** для мгновенного полнотекстового поиска по индексам в оперативной памяти.

### 3. Инфраструктурный тюнинг и оптимизация пулов соединений
* **PostgreSQL & PgBouncer:** Для оптимизации сессионных соединений к PostgreSQL развернут и сконфигурирован пул-менеджер **PgBouncer** в режиме *Transaction Pooling*. Это полностью ликвидировало сетевые издержки на TCP-рукопожатия (handshake) при частых запросах.
* **Реализован безопасный обход ограничений PgBouncer:** Настроено временное переопределение хостов для выполнения DDL-миграций Django напрямую в PostgreSQL, так как миграции требуют долгоживущих сессионных соединений и не могут выполняться в режиме Transaction Pooling.
* **Redis Connection Pools:** Проведена точечная оптимизация пулов постоянных сокетов во встроенных клиентах бэкенда (`django-redis` и асинхронных драйверах FastAPI). Жесткое ограничение параметра `max_connections` устранило оверхед на повторные handshake-соединения в NoSQL-слое.

### 4. Асинхронная шина данных (Redis Streams) и Event-Driven синхронизация
Синхронизация данных об остатках товаров между PostgreSQL (мастер-источник) и распределенным кэшем инстансов Redis выстроена по событийно-ориентированному паттерну (Event-Driven). Изменения транслируются асинхронно через высокопроизводительную шину сообщений на базе **Redis Streams**.

### 5. Автоматический прогрев кэша (Warmup) при деплое
Для исключения проблемы *Cache Cold Start* (когда после перезапуска контейнеров 3k RPS бьют в пустой кэш и создают лавинообразную нагрузку на СУБД) реализована система автоматического прогрева кэша каталога в Инстансе 4 через `entrypoint.sh`. 
* Прогрев инициализируется кастомной Django management-командой `BaseCommand`. 
* Архитектура команды защищена от циклических импортов (*Circular Imports*) за счет ленивой загрузки таски внутри метода `handle` и асинхронно отправляет задачу полной заливки каталога в Celery.

### 6. Консистентность данных и сетевая безопасность
* **Атомарность операций:** Полностью исключены состояния гонки (*race conditions*) при одновременном оформлении заказов. Слияние корзин, проверка и списание складских остатков атомарно инкапсулированы на уровне Redis с помощью кастомных транзакционных **Lua-скриптов (`evalsha`)**.
* **Идемпотентность:** Внедрен механизм строгой идемпотентности API на базе уникальных ключей (*Idempotency Keys*) для защиты от повторных запросов и дублирования заказов при сбоях сети.

### 7. Frontend-интеграция без JS-оверхеда
Создан бесшовный, динамичный пользовательский интерфейс с эффектом SPA без развертывания тяжелой инфраструктуры (React/Node.js) и поддержки сложного клиентского стейта. Динамическое обновление страниц и интерактивность реализованы за счет интеграции Django с фронтенд-библиотекой **htmx**.

## 🛠️ Технологический стек
* **Backend:** Python 3, FastAPI, Django, SQLAlchemy 2.0 Async, Pydantic, Celery, RabbitMQ
* **Databases & Caching:** PostgreSQL, Redis (Streams, RediSearch, Lua scripting), PgBouncer
* **DevOps & Infrastructure:** Docker, Docker Compose, Nginx, Bash (POSIX set -e entrypoints), SSH-туннелирование
* **Testing & Monitoring:** Locust, Pytest

---

## 📈 Текущий статус и запуск
1. Проект разворачивается в гибридной инфраструктуре разработки через `docker-compose.yml`.
2. Кастомный скрипт инициализации контейнеров (`entrypoint.sh`) написан по POSIX-стандарту `set -e` для аварийного завершения при сбоях, предотвращая запуск веб-сервера в невалидном состоянии.
3. Локальное окружение полностью протестировано под стабильные нагрузки в 3000 RPS через Locust. Графики нагрузочных испытаний и конфигурационные файлы персистентности доступны в директории лимитов инфраструктуры.
